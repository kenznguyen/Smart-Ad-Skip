# P2.35 – End-to-End Native Runtime Recovery Validation

## Coverage

Adds `NativeRuntimeRecoveryInstrumentedTest`, which drives the production
`IsolatedQwen3VlRuntime` proxy and manifest-declared `:qwen_native` service on Android.

1. Establishes an observer Binder session and records the process PID/session UUID.
2. Loads the isolated service through the real proxy.
3. Sends frame 101. A debug-only service hook executes a blocking lambda on the real
   `NativeRuntimeLifecycle` single-thread executor, retaining its inference ownership.
4. The proxy inference timeout invokes the production watchdog path. The watchdog validates
   generation, PID, session UUID and process start ticks before killing the isolated process.
5. The observer receives Binder death and Android reconnects the binding. The new process
   reports a new session UUID.
6. Frame 202, queued behind the proxy's operation mutex, is loaded/inferred in the new
   process and returns a response tagged with frame 202.
7. The test verifies frame 101 failed by timeout, the old process disappeared, and frame
   202—not the timed-out request—produced the accepted result.

## Safety boundaries

- Instrumentation hooks are accepted only in a debuggable build and are never enabled in
  release builds. Normal MSG_LOAD/MSG_INFER behavior is unchanged when the hook is absent.
- The blocked lambda runs through the production `NativeRuntimeLifecycle`, so its
  single-flight reservation and native-ownership retention semantics are exercised. Killing
  the isolated process is what reclaims the simulated stuck native worker; no in-process
  ownership flag is force-cleared.
- This is a deterministic native-call surrogate, not a deliberately corrupted llama.cpp/JNI
  kernel or a production model load. It validates the real Android process/Binder/watchdog
  recovery path without requiring large model assets or a flaky native fault.
- P2.23 unit tests continue to cover native ownership when a call eventually returns.
  Device execution is still required to validate this instrumentation scenario on hardware.

## Device execution

Run on a physical ARM64 Android device or ARM64 emulator, API 26+:

```bash
gradle :app:connectedDebugAndroidTest
```

Record device model, API level, ABI, test count and result. Hosted GitHub Actions compiles
and uploads the instrumentation APK but has no attached Android device; a green CI build
does not mean this test ran.
