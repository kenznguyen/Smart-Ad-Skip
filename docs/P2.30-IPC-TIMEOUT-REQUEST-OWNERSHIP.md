# P2.30 – IPC Timeout and Request Ownership

## Timeout budgets

- Service binding: 10 seconds.
- HELLO handshake: 5 seconds; transport-only timeout, never kills the native process.
- LOAD: five times the configured native inference timeout.
- INFER: the configured native inference timeout.

All waits are bounded. A binding timeout explicitly unbinds the failed binding and enters the existing bounded recovery policy. A timed-out waiter does not cancel the shared connection future.

## Ownership and recovery

- Timing out the Kotlin caller removes only that IPC request from the pending map.
- LOAD/INFER cancellation requests process recovery; it does not release a JNI slot in the main process.
- The watchdog compares the native process PID and native elapsed time with the stuck threshold. It kills only the dedicated native process when policy returns TERMINATE_PROCESS.
- If native work has not crossed the stuck threshold, the runtime remains fail-safe; the server-side NativeRuntimeLifecycle continues to own the in-flight call and rejects overlapping inference.
- HELLO timeout is treated as transport failure and follows binding recovery without terminating native execution.
- The shared connection future is not cancelled when an individual waiter times out.
- Parent coroutine cancellation is preserved; only an actual timeout is converted into a connection/handshake timeout failure.

## Verification scope

Unit tests cover timeout budgets and whether each request class is eligible for process termination. Existing NativeRuntimeLifecycle tests cover caller-timeout ownership retention, STUCK classification, duplicate inference rejection, and release only after native return.

Android ServiceConnection failure injection and device-level Binder death/reconnect testing remain separate integration coverage; CI does not prove those runtime behaviors.
