# P2.20 — Native Resource Safety

## Scope

This change hardens the Qwen3-VL JNI boundary without changing model prompts, output parsing, action selection, target authorization, or Accessibility behavior.

## Ownership and cleanup

- `ScopedUtfChars` pairs every successful `GetStringUTFChars` with `ReleaseStringUTFChars`, including C++ allocation/formatting exceptions.
- `ScopedIntArray` pairs every successful `GetIntArrayElements` with `ReleaseIntArrayElements(..., JNI_ABORT)`. Screenshot pixels are read-only and are never copied back to Java.
- Runtime construction remains transactional: the candidate runtime is held by `std::unique_ptr` until model, context, vision context, and chat templates all initialize. Any failed stage destroys already-created dependencies.
- Runtime destruction preserves dependency order: chat templates, MTMD vision context, llama context, then model.
- Sampler chain uses a custom-deleter `unique_ptr`; the chain owns the greedy sampler after it is added.
- `BatchOwner` releases `llama_batch` during normal return and every exception path.
- MTMD input chunks and bitmap data retain their library-provided RAII owners.

## Failure behavior

Native exceptions are translated to `IllegalStateException` at the JNI boundary. Inference failures return no result and cannot bypass the existing Kotlin lifecycle serialization. The lifecycle remains unavailable immediately after close is requested, and destruction stays queued behind active native work.

## Regression tests

`NativeResourceFailureTest` injects inference and close failures at the JNI lifecycle boundary and verifies:
- failed inference does not prevent subsequent native close;
- repeated close requests share one cleanup operation;
- a failed native close still leaves the lifecycle in CLOSED.

Existing lifecycle tests continue to cover failed load, close during active inference, and inference rejection after close.

## Verification

The Android CI workflow must pass unit tests and assemble the arm64-v8a debug APK. This does not replace physical-device stress testing with real GGUF files. No claim of native allocator fault-injection coverage is made by the JVM lifecycle tests.
