# P2.40 – Bounded Ad Monitoring

## Scope

Re-observe a positively identified Fruit Blast ad after Qwen3-VL returns `WAIT`, even when the Accessibility event stream becomes quiet. Monitoring is bounded and tied to the same verified application window.

## Behavior

- A monitoring session starts only after `AdStateClassifier` positively identifies `AD_PLAYING` or `SKIP_AVAILABLE`.
- A `WAIT` decision schedules a fresh Accessibility observation with exponential backoff: 1.5s, 3s, 6s, 8s, 8s, 8s.
- At most six automatic re-observations are scheduled per session.
- Before scheduling and before every tick, the service rechecks the target package, the same Accessibility window ID, and capture eligibility.
- A real window-state transition, ad completion, foreground change, unbind, or destroy ends the session and cancels pending work.
- A successful authorized click resets the per-ad monitoring budget.
- Screenshot capture continues through the existing single-flight lifecycle and minimum capture interval.

## Safety boundaries

- A monitor tick is a new observation, not a click instruction.
- Every AI action still passes the existing frame freshness, foreground validity, action allowlist, confidence, target safety, live-node identity, and final click authorization gates.
- Root-only MIUI fallback may permit capture, but it never upgrades `isValid`; click authorization remains denied unless the full active-window identity is verified.
- `UNKNOWN` and unverified ad contexts are not promoted to actionable states by the monitoring loop.
- Inference failures and timeouts stop the monitoring session rather than repeatedly retrying a failed native runtime.

## Verification

Unit tests cover exponential backoff, maximum cycle count, foreground/ad eligibility, reset behavior, and budget exhaustion. Android CI is configured to run on pushes to the active P2.17 feature branch as well as `main`.

Physical Xiaomi/MIUI validation remains required for device-specific Accessibility window behavior.
