# P2.32 – Binder Lifecycle Race Testing

## Android instrumentation coverage

`NativeInferenceProcessServiceInstrumentedTest` binds the actual manifest-declared service in the isolated `:qwen_native` process. It sends a Messenger HELLO request and verifies:
- the Binder endpoint responds from a PID distinct from the instrumentation process;
- the response echoes the request's binding generation;
- the isolated process exposes a non-empty process-session UUID;
- terminating that isolated PID produces a Binder disconnect callback;
- Android reconnects the still-bound ServiceConnection;
- the restarted process returns a different session UUID.

This exercises the real Android Service, Binder transport, process boundary, death notification and automatic reconnect without loading multi-gigabyte model files or invoking JNI inference.

## Run on Android

The app currently packages native libraries for `arm64-v8a`. Run the instrumentation suite on an ARM64 Android device or ARM64 emulator with API 26+:

```bash
gradle :app:connectedDebugAndroidTest
```

The standard CI workflow compiles the instrumentation APK and publishes it as `smart-ad-skip-debug-android-test-apk`. The current hosted CI runner does not provide a configured ARM64 Android device, so compilation in CI is not reported as execution of the instrumentation test.

## Race coverage boundaries

- Stale callback / old generation rejection remains covered by `NativeProcessSessionPolicyTest` and the generation checks in the proxy; this instrumentation test additionally verifies generation propagation across real Binder messages.
- Binder process death and automatic reconnect are exercised against Android itself.
- The test kills the isolated service PID to reproduce the process-death event that watchdog recovery must handle. It does not invoke the proxy's private watchdog method or claim to prove the watchdog's concurrent timeout/kill race.
- `onBindingDied` and `onNullBinding` are not deterministically inducible through this bound service contract; those callback branches remain guarded by generation-scoped production handling and need a dedicated controllable test service or platform fault-injection harness.
- Actual delayed reply delivery racing a reconnect, concurrent timeout cancellation, and watchdog-vs-reconnect scheduling still require a controllable Binder test endpoint or device fault-injection test. Do not treat APK compilation as proof of these races.

The test intentionally asserts a new process-session UUID rather than a different PID because Linux may reuse a PID. P2.31's PID plus process-start-time identity checks remain the guard against PID reuse.
